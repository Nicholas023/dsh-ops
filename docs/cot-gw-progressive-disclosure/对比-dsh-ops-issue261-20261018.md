## 二、cot-gw 已验证、可贡献给 0.4.0 的经验（261 未写明的）

1. **前缀字节稳定是缓存命中的硬前提**：动态工具面（早期 LRU 版）破坏前缀、缓存失效 → 静态台面+尾部增长才是稳定形态。PTC 若想激进省 token，工具 schema 必须静态化或批处理化。
2. **「工具够得着 ≠ 会被想起」**：第四种到达方式是时机提醒（tool-nudge）。0.4.0 PTC 批处理工具「高能力但低频」，更需要结果驱动提醒兜底。
3. **剥工具/知识的度**：剥到极致会诱发「为了找能力反复搜索」（实测 17 次空搜 = 更贵+质量降级）——保留紧凑索引（名+一句话）。
4. **台面怎么选**：A 层调用频率 + B 层替代证据 + 岗位政策三判据（不是拍脑袋）。
5. **收益边界与止损**：高频×长会话才值得做；命中率 96→97.5% 收益趋零别追；预设单任务 >5 万 token 熔断。
6. **验证协议**：端到端双基线（逐字一致+独立新会话）+ 拆解未命中/命中/输出三数 + 两次复测 <15% + 质量 ✗/⚠ 守门——0.4.0 拆分 Native/PTC 后的回归验证可直接搬。

## 三、本质差异（定位不同层）

| | cot-gw | #261 / 0.4.0 |
| --- | --- | --- |
| 优化对象 | **同一执行层内**的「工具面组织」：模型每步看到的 tools 数组与说明书 | **执行层之间**的「分方案」：Native 与 PTC 的实现与调用方式分开走 |
| 形态 | 一套预设（resident + gateway 抽屉） | ops 工具集整体架构（Native 轻量化、PTC 激进省 token） |
| 与渐进式披露关系 | 披露手法本身（机制层） | 把披露上升为**项目原则**（方法论层） |

关系：cot-gw = 0.4.0 的「工具面组织层」既有答案；0.4.0 在其上叠加「执行层分方案」，原则 3 直接复用 cot-gw 的名词与手法。

## 四、结论

- 4 条原则中 **3 条（目的 / 手段 / 轻量低侵入）cot-gw 已有实现与实测数据支撑**，原则 2 部分吻合（附加工具、联动独立 ✅；覆盖原版工具、ops_bash 封装 ❌ 属 261 新增）。
- 若 0.4.0 落地，cot-gw 全集可直接充当三份参考：**机制参考**（gateway / tool-gate / tool-watch / tool-nudge 四件套）、**验证协议参考**（省钱思路 §4）、**避坑清单**（LRU 破坏前缀、剥过度引发空搜、追命中率无收益）。
